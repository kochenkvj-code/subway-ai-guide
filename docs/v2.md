# V2 development route

`/` retains the original passenger interface. `/v2` introduces the approved navy
home, nine menu entries and a separate AI chat entry. The original guide has been
moved into `app/components/GuideExperience.jsx`; the root page and V2 both use it.
API handlers, routing rules, gate instructions, fare copy and facility maps are
shared, not reimplemented. The previously deferred English/Japanese/Chinese home
copy update is included.

Connected now: route search, gate errors, tickets/cards, station facilities, AI
chat. Attractions, found-item search, train-left-item assistance, live trains and
station feedback are visibly marked coming soon. The train overview deliberately
shows no simulated arrival times. The discovery banner leads to the pending
attractions screen; it does not yet request GPS or call TourAPI.

V2 uses full-screen feature views and native language selection. Its `view` query
parameter supports direct links and browser back/forward. Lazily mounted guide
panes keep their state while switching home/features, and the chat retains its
existing bounded provider context. State is in memory, not retained after a full
reload. V2 records page/activity statistics once at the shell, not per guide pane;
the existing per-browser analytics exclusion also applies. Menu/language/action
statistics reuse the existing collectors. Test browsers should enable exclusion
from the authenticated `/admin/stats` control.

The station is still Jongno 5-ga as in the current application; per-station URLs
and dynamic routing origins are subsequent work. Secrets and existing server API
configuration are reused, with no client-side credentials.

Validation: production build; existing 8 chat-context/provider/language-scroll
tests; isolated browser checks of all five connected features, route response and
chat history with mocked providers, retained selections/results, four languages,
app/browser back, direct links, one page event, original root and gate QR flow.

## Mobile input and home scroll

Embedded guides must not apply the original standalone page's `html, body`
height/overflow lock. Their styles use a non-document selector for those rules;
the original root keeps its existing mobile scrolling behavior. V2 text inputs,
textareas and selects use at least 16px to avoid iOS focus auto-zoom, without
restricting user pinch zoom. View activation blurs the previous input to dismiss
its keyboard before restoring the destination view.

Regression verification used mobile Chromium touch start/move/end gestures after
all four guides and home/app-back/browser-back-forward navigation. It also checked
computed input font sizes, keyboard focus release, the unchanged root scroll
policy and the eight existing context/scroll tests. Physical iPhone Safari was
not available in the execution environment.

## Real-time arrivals

The top card and live-train entry now use `/api/train-arrivals` and the server-only
`SEOUL_SUBWAY_ARRIVAL_API_KEY`. Position-map functionality and
`SEOUL_SUBWAY_POSITION_API_KEY` are not used yet. Arrival polling runs every 30
seconds only while the home/arrival view and browser tab are visible. Identical
server requests coalesce and use a 15-second cache; no provider URL containing a
key is returned or logged.

The official Seoul arrival API's HTTP service endpoint is used server-to-server;
the browser calls our HTTPS route. The public sample only allows Seoul Station.
Reference: https://data.seoul.go.kr/dataList/OA-12764/A/1/datasetView.do
Provider timestamps are parsed as KST. Estimates account for time elapsed since
`recptnDt`. Departed trains, invalid timestamps, feed records older than three
minutes and old arrived/entering states are suppressed. Unknown or elapsed ETAs
are never rendered as zero minutes or a fabricated arrival. Failures hide prior
estimates and offer retry. Arrival details distinguish the next-station direction
from each train's destination and show provider timestamps/train numbers.

`npm run test:arrivals` exercises normalization, time correction, stale/departed
filtering, no-data, endpoint key absence, caching/coalescing and safe errors.
Browser checks cover summaries/details, 30-second updates, off-screen pause,
resume, retries, failure suppression and four-language mobile layout. Production
credentials are verified after deployment; they are not present locally.
