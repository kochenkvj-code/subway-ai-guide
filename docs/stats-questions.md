# AI question records and reliable event delivery

AI request events now include up to 500 characters of the visible question, the existing language and anonymous session, and the original client event timestamp. The admin stats page lists these separately in reverse chronological order, with KST timestamps and 25-row pagination under the existing date filter. Older events display “내용 미수집”. AI answers are not stored. This also includes existing AI-backed facility guide requests. Four-language notices describe storage for service improvement.

Apply database/stats-question-reliability.sql before releasing the client/API changes. It adds nullable columns and a unique event ID index, preserving old clients and data. No public read permissions are added; the existing authenticated admin report is the only reader exposed by this application.

Pending events are saved in sessionStorage before sending, scoped to the existing anonymous tab session, with at most 100 entries. Successful DB acknowledgement (HTTP 204) removes them. Network failures, timeouts, 403 challenges, 408, 429 and server errors retry with the same event ID, payload and original click time. Backoff starts at two seconds and is capped at one minute. Reconnect, visibility changes, page return and page hide also trigger a retry, with at most four requests in flight. Each request has a 12-second client timeout and an 8-second upstream DB timeout.

The retry window is 30 minutes; expired entries are discarded before reuse, including after suspension/reload. Pending question text is included only for AI question events (maximum 500 characters) in this tab-scoped queue. No localStorage or cross-tab recovery is introduced. Blocked or full storage falls back to memory. Explicit analytics opt-out clears the queue and disables new collection. HTTP 400/404/405/410/413/422 remove permanently invalid entries. A closed tab or browser failure can still lose events; this is not guaranteed delivery.

PostgREST ignores duplicate event IDs using the existing unique index. No database migration is required for this update. The server accepts original event timestamps up to 35 minutes old to accommodate the retry window and request delay; future skew remains limited to five minutes. The date report filters on occurred_at, with created_at fallback for legacy null timestamps, so a retry after midnight belongs to its original day. Session rows are ordered by their first event (the displayed entry time) descending; events within a session remain chronological.

Server validation and DB failures log a stage, event UUID and validated event type/name where available. They do not log question text, session IDs, IPs, user agents, cookies or credential-bearing URLs. These logs cannot prove whether an unreceived browser tap occurred.

Verification: `npm run test:stats` covers retries past four attempts, stable IDs/timestamps, reload recovery, retention, opt-out cleanup, blocked/corrupt/cross-session storage, concurrency limits, API diagnostics and date boundaries. After `npm run build`, `npm run test:stats-ui` runs an isolated production browser/API/fixture-DB flow: failed event delivery does not prevent guidance, reload restores the same payload, uncertain acknowledgements cause safe duplicate requests, queue clears after success, and overlapping sessions sort by displayed entry time. It writes no production analytics. Live DB schema inspection and read-only query checks verify that the deployed unique ID index and date filters are available.
